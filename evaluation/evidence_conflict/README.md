# NLI Stance Diagnostic Benchmark

This directory contains a small, manually curated diagnostic benchmark for the
three-class NLI stance classifier in `src/evidence_conflict/nli_classifier.py`.
It is intended to expose obvious label-mapping, integration, and failure-mode
problems before ECS scoring is implemented.

It is **not** a representative benchmark, a statistically powered evaluation,
or proof of general factual reliability. The results are sensitive to dataset
construction and to the exact phrasing of claims and evidence.

## Dataset

`data/nli_stance_benchmark_v1.json` contains 90 claim-evidence pairs:

- 30 `supports`
- 30 `refutes`
- 30 `not_enough_info`

Each example has a stable ID, claim, evidence, gold label, rationale, and
category. Gold labels describe the semantic relationship between evidence and
claim; they were not generated by the model under evaluation. Genuinely
ambiguous cases were excluded from the scored set.

The examples cover direct support and contradiction, related but non-decisive
evidence, unrelated evidence, overlapping vocabulary with a different meaning,
numerical and date-based claims, named entities and locations, negation, and
simple paraphrases. The three earlier smoke-test examples are not used as the
scored dataset.

## Runner

Run real local inference from the project root with the project environment:

```powershell
.\venv\Scripts\python.exe -m evaluation.evidence_conflict.benchmark `
  --batch-size 2 `
  --local-files-only
```

The model is loaded lazily through the existing `NLIStanceClassifier`. A single
classifier instance is reused for all examples. The first `predict` call
includes tokenizer/model loading; warm timings exclude that first call.

Reports are written by default to:

- `evaluation/evidence_conflict/results/nli_stance_benchmark.json`
- `evaluation/evidence_conflict/results/nli_stance_benchmark.md`

Model-comparison artifacts from the current diagnostic phase are:

- `evaluation/evidence_conflict/results/nli_stance_benchmark_xsmall_remeasured.json`
- `evaluation/evidence_conflict/results/nli_stance_benchmark_xsmall_remeasured.md`
- `evaluation/evidence_conflict/results/nli_stance_benchmark_deberta_v3_base.json`
- `evaluation/evidence_conflict/results/nli_stance_benchmark_deberta_v3_base.md`
- `evaluation/evidence_conflict/results/nli_model_comparison.json`
- `evaluation/evidence_conflict/results/nli_model_comparison.md`

Use `--dataset`, `--output-dir`, or `--output-prefix` to change paths. Use
`--model`, `--model-revision`, `--device`, `--max-length`, `--batch-size`, or
`--confidence-threshold` only for an explicit diagnostic comparison. The
project's default model is not changed by this runner.

The runner records a process-level peak working set on Windows using
`GetProcessMemoryInfo` when available. This is not isolated model-weight
memory; it includes the Python process, imported libraries, tokenizer, model,
and inference workspace.

## Model comparison

An explicit model override can be evaluated on the same frozen dataset:

```powershell
.\venv\Scripts\python.exe -m evaluation.evidence_conflict.benchmark `
  --model MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli `
  --model-revision 6f5cf0a2b59cabb106aca4c287eed12e357e90eb `
  --batch-size 2 `
  --local-files-only `
  --output-prefix nli_stance_benchmark_deberta_v3_base
```

Compare two completed JSON reports without loading a model or recomputing
predictions:

```powershell
.\venv\Scripts\python.exe -m evaluation.evidence_conflict.compare_nli_models `
  --baseline evaluation/evidence_conflict/results/nli_stance_benchmark_xsmall_remeasured.json `
  --alternative evaluation/evidence_conflict/results/nli_stance_benchmark_deberta_v3_base.json `
  --baseline-label "Existing xsmall" `
  --alternative-label "Alternative base" `
  --output-prefix nli_model_comparison
```

The comparison writes `nli_model_comparison.json` and
`nli_model_comparison.md`. It reuses the measured metrics, confusion matrices,
timings, and failures from the source reports; it does not change the dataset,
gold labels, metric definitions, or production model.

The evaluated alternative checkpoint loaded in `torch.float16` on CPU because
its checkpoint configuration declares that dtype; the xsmall baseline loaded in
`torch.float32`. The existing classifier was not modified to override dtype, so
CPU runtime comparisons include that difference. The alternative tokenizer used
the fast DeBERTa v3 tokenizer and did not require `sentencepiece`.

## Metric conventions

- Accuracy, macro-F1, and per-class precision/recall/F1 use **successful
  predictions only**. The report states this denominator explicitly.
- Inference failures are recorded separately, are never counted as correct,
  and also contribute to `accuracy_including_failures_as_incorrect` and
  per-class `recall_including_failures`.
- Macro-F1 uses the fixed three-label set. A class absent from a small fixture
  contributes 0 rather than being silently dropped.
- Confusion-matrix rows are gold labels and columns are predicted labels, in the
  canonical order `supports`, `refutes`, `not_enough_info`.
- Confidence is the model's maximum class probability, not a calibrated
  probability of correctness.

## Unit tests

```powershell
.\venv\Scripts\python.exe -m pytest `
  tests/evidence_conflict/test_nli_benchmark.py `
  tests/evidence_conflict/test_nli_model_comparison.py -q
```

The unit tests use fake classifiers, synthetic comparison reports, and
in-memory datasets. They do not import PyTorch or Transformers, download
weights, or call external services. The real benchmark is an explicitly invoked
slow/integration run.
